# ADR-004: Timestamps como TEXT ISO 8601 UTC e agregação de `clicksByDay` via CTE recursiva

## Status

Accepted

## Date

2026-09-21

## Context

`clicksByDay` precisa cobrir exatamente os últimos 30 dias a partir de "hoje",
incluindo dias com zero cliques (Business Rules do PRD), comparando contra o
instante fornecido pelo `Clock` injetado (ADR-003), não contra o relógio real da
máquina. SQLite não tem tipo nativo de data/hora, e a extensão `generate_series`
não vem habilitada por padrão no binário do `better-sqlite3`. Duas decisões técnicas
precisam ser tomadas: (1) o tipo/formato de coluna para `created_at`/`expires_at`;
(2) a estratégia de query que produz os 30 dias zero-preenchidos sem lógica de
preenchimento em JavaScript. Decisão tomada unilateralmente por pedido explícito de
priorizar velocidade.

## Decision

Timestamps são armazenados como `TEXT` em formato ISO 8601 UTC
(`clock.now().toISOString()`), em `links.created_at`, `links.expires_at` e
`clicks.created_at`. Comparação de expiração (`expires_at <= :now`) e ordenação
(`ORDER BY created_at DESC`) usam comparação lexicográfica de string — equivalente à
ordem cronológica para ISO 8601 UTC de largura fixa.

A série de 30 dias de `clicksByDay` é gerada inteiramente em SQL com uma CTE
recursiva (`WITH RECURSIVE`) que conta de 0 a 29 a partir de um `:today` (data
`YYYY-MM-DD` calculada em código a partir de `clock.now()`, nunca de
`CURRENT_TIMESTAMP`/`date('now')` do SQLite) e faz `LEFT JOIN` com `clicks`
agrupando por dia — zero-fill acontece no próprio SQL, sem loop de preenchimento na
aplicação. Ver `_techspec.md` (Data Models) para o SQL completo.

## Alternatives Considered

### Alternative 1: Coluna `INTEGER` com timestamp Unix (ms)

- **Descrição**: armazenar `created_at`/`expires_at` como epoch em milissegundos.
- **Prós**: comparação numérica nativa, sem depender de formato de string.
- **Contras**: perde legibilidade ao inspecionar o banco manualmente durante o
  desafio; extrair "o dia" exige `datetime(ts/1000,'unixepoch')`, mais verboso que
  `date(created_at)` sobre uma string ISO.
- **Por que rejeitado**: sem ganho de performance mensurável no volume do desafio;
  legibilidade vale mais que a microotimização.

### Alternative 2: Agregar por dia em JavaScript (buscar cliques, `reduce`/`Map`)

- **Descrição**: buscar todos os cliques do link e agregar/zero-preencher os 30 dias
  em código de aplicação.
- **Prós**: não depende de CTE recursiva; mais legível para quem não conhece SQL
  avançado.
- **Contras**: contraria a justificativa central do ADR-001 ("SQLite resolve
  `clicksByDay`/`topReferrers` com `GROUP BY` nativo"); traz toda a tabela de
  cliques do link para a memória da aplicação a cada consulta de stats; duplica em
  JS uma responsabilidade de agregação que é o motivo declarado de se usar SQL real.
- **Por que rejeitado**: reabre exatamente o trade-off que o ADR-001 já resolveu a
  favor de agregação via SQL.

### Alternative 3: Extensão SQLite `generate_series`

- **Descrição**: usar a função de tabela `generate_series` para gerar os 30 dias.
- **Prós**: sintaxe mais direta que uma CTE recursiva.
- **Contras**: não vem habilitada por padrão no binário pré-compilado do
  `better-sqlite3` — exigiria carregar extensão nativa, adicionando fricção de setup.
- **Por que rejeitado**: contraria o requisito central do ADR-001 ("roda com um
  comando", zero dependência externa).

## Consequences

### Positive

- Nenhuma lógica de data em JavaScript para preencher os 30 dias — reduz superfície
  de bug de fuso horário/off-by-one.
- Dado legível a olho nu ao inspecionar o arquivo `.sqlite` diretamente.
- "Hoje" vem do `Clock` injetado (ADR-003), mantendo a agregação determinística em
  teste.

### Negative

- Comparação lexicográfica de string exige disciplina de sempre gravar timestamps em
  UTC com o mesmo formato (`toISOString()`); qualquer escrita fora desse padrão
  quebraria ordenação/comparação silenciosamente.
- CTE recursiva é menos familiar que SQL básico para quem revisar o código depois.

### Risks

- Formato de timestamp inconsistente introduzido em algum ponto do código quebraria
  comparação/ordenação sem erro explícito — mitigado por concentrar toda escrita de
  timestamp atrás dos repositories (nenhum outro lugar do código formata data para
  persistência).

## Implementation Notes

- A query de `clicksByDay` recebe `:today` como parâmetro (`YYYY-MM-DD`) calculado a
  partir de `clock.now()` em código, nunca de `date('now')` do SQLite — evita
  reintroduzir um relógio não injetado dentro do banco.
- SQL completo (schema, índices, query de `clicksByDay` e `topReferrers`) documentado
  em `_techspec.md`, seção "Data Models".
