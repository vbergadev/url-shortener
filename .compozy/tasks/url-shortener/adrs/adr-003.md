# ADR-003: Arquitetura em camadas com dependências injetáveis (clock, gerador de código)

## Status

Accepted

## Date

2026-09-21

## Context

O PRD e o ADR-002 exigem testes determinísticos (`CLAUDE.md`, regra 1.3), e um dos code
smells críticos listados em `CLAUDE.md` (#6) é "acoplamento com detalhe de
infraestrutura — regra de negócio importando driver de banco, framework HTTP ou SDK
direto". Precisamos decidir, antes de qualquer código, (1) como as camadas do serviço
se dividem e (2) como tempo (`Date.now()`) e aleatoriedade (geração de short code)
entram no sistema sem tornar os testes flaky nem exigir mock de módulo global.
Decisão tomada unilateralmente (sem pergunta ao usuário) por pedido explícito de
priorizar velocidade no desafio de 1h.

## Decision

Três camadas, com dependência de import em um único sentido (routes → services →
repositories):

- **routes** (Fastify): parsing HTTP, schemas JSON de request/response, delega a um
  service e mapeia erros tipados de domínio para status HTTP. Não contém regra de
  negócio nem SQL.
- **services**: regra de negócio pura de domínio (encurtar, redirecionar, listar,
  agregar estatísticas). Não importam Fastify nem `better-sqlite3` — recebem
  repositórios e dependências transversais já construídos.
- **repositories**: único lugar do código que importa `better-sqlite3` e escreve SQL.

Duas dependências transversais são injetadas explicitamente na construção do app/
serviços em vez de acessadas globalmente:

- `Clock` — `{ now(): Date }`. Implementação real (`systemClock`) usa `new Date()`;
  testes usam um clock fixo.
- `CodeGenerator` — `{ generate(): string }`. Implementação real
  (`randomCodeGenerator`) gera 7 caracteres alfanuméricos via `crypto.randomInt`;
  testes usam um gerador com fila de valores pré-definidos (para forçar colisão
  determinística — ver ADR-002).

A composição é feita por uma factory function `buildApp(deps)`, sem container de DI.

## Alternatives Considered

### Alternative 1: Handlers Fastify chamando SQL diretamente (sem camada de serviço)

- **Descrição**: cada rota Fastify já contém a query SQL e a regra de negócio inline.
- **Prós**: menos arquivos, mais rápido de escrever em 1h.
- **Contras**: viola diretamente o code smell crítico #6 do `CLAUDE.md` (handler vira
  "deus" misturando HTTP + SQL + regra de negócio); impossível testar a regra de
  negócio (ex.: cálculo de expiração) sem subir Fastify e SQLite juntos.
- **Por que rejeitado**: a regra do projeto proíbe explicitamente esse acoplamento;
  não é uma troca aceitável mesmo sob pressão de tempo.

### Alternative 2: `Date.now()`/`Math.random()` direto nos services, sem `Clock`/`CodeGenerator`

- **Descrição**: services chamam as APIs globais de tempo e aleatoriedade diretamente.
- **Prós**: menos uma interface/arquivo.
- **Contras**: testes de expiração (`expiresAt === now`, borda inclusiva) e de colisão
  de short code deixam de ser determináveis sem recorrer a mock de módulo global
  (`vi.setSystemTime`, `vi.mock('crypto')`), o que a regra 1.3 do `CLAUDE.md` pede
  para evitar em favor de injeção explícita.
- **Por que rejeitado**: contraria diretamente a regra de testes não-flaky do
  `CLAUDE.md`.

### Alternative 3: Container de injeção de dependências (ex.: tsyringe, InversifyJS)

- **Descrição**: usar um container de DI com decorators para resolver as dependências.
- **Prós**: padrão comum em aplicações maiores.
- **Contras**: abstração prematura (code smell #7) para 5 services e 2 dependências
  transversais; overhead de setup e curva de configuração incompatíveis com o
  orçamento de 1h.
- **Por que rejeitado**: YAGNI — uma factory function resolve o mesmo problema sem
  dependência nova.

## Consequences

### Positive

- Services 100% testáveis sem Fastify nem arquivo de banco real.
- Troca de driver SQL (ex.: outro driver SQLite) não vaza para a regra de negócio.
- Testes de expiração e de colisão de short code totalmente determinísticos.

### Negative

- Uma function factory a mais (`buildApp`) por dependência transversal.
- Um pouco mais de boilerplate para passar `clock`/`codeGenerator` explicitamente
  para dentro dos services, em vez de importá-los globalmente.

### Risks

- Nenhum bloqueante identificado para o escopo do desafio.

## Implementation Notes

- `buildApp({ db, clock, codeGenerator })` retorna uma instância Fastify configurada
  mas **sem** escutar porta (usada em teste via `app.inject()`).
- `server.ts` é o único ponto que chama
  `buildApp({ db: openConnection(config.databaseUrl), clock: systemClock, codeGenerator: randomCodeGenerator })`
  seguido de `.listen()`.
- Testes chamam
  `buildApp({ db: openConnection(':memory:'), clock: fixedClock(...), codeGenerator: fakeCodeGenerator([...]) })`.
