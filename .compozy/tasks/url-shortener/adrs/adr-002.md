# ADR-002: Geração de short code — aleatório com retry em colisão, sem dedupe de URL

## Status

Accepted

## Date

2026-09-21

## Context

O gist pede short code com ~7 caracteres alfanuméricos, mas não especifica o
algoritmo de geração nem o que fazer se a mesma URL for encurtada duas vezes. Duas
decisões de negócio precisam ser tomadas para o comportamento ser determinístico e
testável: (1) como o código é gerado e o que acontece em colisão; (2) se
`POST /api/shorten` com a mesma URL duas vezes deve reaproveitar o código existente
ou sempre criar um novo registro.

## Decision

- Código gerado aleatoriamente a partir de alfabeto alfanumérico (`[A-Za-z0-9]`),
  7 caracteres. Em colisão (código já existe), gera-se outro e tenta de novo (poucas
  tentativas — espaço de ~62^7 torna colisão real virtualmente impossível no volume
  do desafio).
- **Sem dedupe**: cada chamada a `POST /api/shorten` cria um novo registro e um novo
  short code, mesmo que a `url` já tenha sido encurtada antes. É o comportamento mais
  simples e é o que o contrato do endpoint sugere (não há menção a idempotência ou
  reaproveitamento).
- Não há suporte a short code customizado (usuário escolher o próprio código) — não
  foi pedido no gist.

## Alternatives Considered

### Alternative 1: Código sequencial em base62 (contador incremental)

- **Descrição**: id auto-incremento do banco convertido para base62.
- **Prós**: sem colisão possível, sem retry.
- **Contras**: código previsível/enumerável (short code N+1 revela quantos links
  existem, e permite varrer todos os links da base); menos "parece" com um short
  code de produto real.
- **Por que rejeitado**: enumerabilidade é uma falha de design pra um serviço público
  de encurtamento — não vale o ganho de simplicidade.

### Alternative 2: Dedupe por URL (reaproveitar código se a URL já existe)

- **Descrição**: antes de criar, busca se a `url` (+ `expiresAt`?) já tem um código
  ativo e devolve o mesmo.
- **Prós**: evita registros duplicados para a mesma URL.
- **Contras**: introduz regra de negócio não pedida (o que conta como "mesma URL"?
  normalizar trailing slash, query string, case? o que fazer se o `expiresAt` for
  diferente na segunda chamada?) — ambiguidade que não vale abrir dado o pedido
  explícito de ir rápido e não miudar regra de negócio não especificada.
- **Por que rejeitado**: YAGNI — não foi pedido, e abrir essa regra custaria tempo de
  design desproporcional ao benefício no escopo do desafio.

## Consequences

### Positive

- Comportamento simples de implementar e de testar (gerar código, checar unicidade,
  persistir).
- Sem enumerabilidade sequencial.

### Negative

- Mesma URL gera múltiplos short codes ao longo do tempo (aceito — ver Non-Goals
  no PRD).

### Risks

- Colisão em teoria possível — mitigada por retry com nova geração; constraint
  `UNIQUE` no banco garante que uma colisão nunca é persistida silenciosamente.

## Implementation Notes

- Geração isolada atrás de uma função injetável (`generateCode()`), para testes
  poderem forçar colisão determinística sem depender de aleatoriedade real
  (ver regra de testes não-flaky em `CLAUDE.md`).
